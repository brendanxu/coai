## Manual Verify Checklist (founder)

Steps to run after `bin/v22-deploy.sh up`:

1. User login → navigate to `/setting/tokens` — page loads, no crash
2. Click "新建令牌" → enter name → submit → plaintext `sk-tnx-xxx` appears in modal
3. Close modal → token list shows masked `sk-tnx-***-{last4}` + status badge "Active"
4. Click copy icon on masked key → toast "已复制" appears
5. Use the plaintext key in a real curl: `curl -H "Authorization: Bearer sk-tnx-xxx" https://api.greentokey.com/v1/chat/completions -d '{"model":"...","messages":[...]}'` → HTTP 200
6. Refresh `/setting/tokens` → "Used" quota shows +N (tokens consumed)
7. Click rename icon → enter new name → confirm → list shows new name
8. Create a second token → revoke the first → list shows 1 active + 1 revoked
9. Try to revoke the last active token → warning dialog appears + request rejected with "cannot revoke last active token"
10. Navigate to `/admin/gtk?tab=tokens` (or click "令牌审计" tab in admin hub) → admin token table visible
11. Enter a coai_user_id in the search box → filtered results appear → click "强制撤销" → token flips to revoked in list
12. Click audit icon on any token → audit drawer opens (shows history or "暂无记录")

## Risk / Rollback

- **Risk**: Low for DB migration (addColumnIfMissing is idempotent, no data destruction). Medium for frontend (new route + admin tab — isolated from existing tabs).
- **Schema change**: `ALTER TABLE gtk_app_usage_log ADD COLUMN token_id INT NULL` — additive, backward-compatible.
- **Rollback**: `bash bin/v22-deploy.sh rollback` → restores v0.33.0-admin-orphan-cleanup in ~30s. The `token_id` column remains in the DB (safe — it's nullable, existing code ignores it).
- **Backup**: `/opt/greentokey/coai-source.bak.v1.0.<HHMM>/` + `docker-compose.yml.bak.v1.0.<HHMM>/` created by v22-deploy.sh rsync step.
